# 0003. LLM 응답을 강제 tool-call이 아니라 구조화 출력으로 받는다

## Status

Accepted

## Context

`generateCritiqueAndPremises`는 도입 당시(#42)부터 강제 tool-call
(`tools` + `tool_choice: { type: "tool" }`)로 structured output을 받아 왔다. few-shot 예시도
같은 포맷을 맞추려고 assistant 턴의 `tool_use` 블록으로 구성했다.

이 방식에서 두 가지 결함이 실사용에 드러났다.

**1. `premises` 필드 누락 (#58 최초 보고).** 모델이 tool 입력에서 `premises`를 종종 빠뜨렸다.
당시엔 프롬프트/스키마 신뢰도 문제로 추정했으나, 실측해 보니 원인은 `max_tokens = 2048`
절삭이었다. `premises`는 스키마의 마지막 필드라 출력이 잘리면 이 필드부터 통째로 사라진다.
현재 설정 5회 중 1회에서 `stop_reason: "max_tokens"`, `out_tokens: 2048`과 함께 재현됐다.

**2. 사용자 화면에 노출되는 한국어가 대량으로 깨짐.** S3 결과 화면에 `버긥`(비교),
`달라믍니다`, `따뚬` 같은 문자열이 실제로 노출됐다. 조사 결과:

- 인코딩 문제가 아니다 — 응답 원문에 `\uXXXX` 이스케이프가 하나도 없고 전부 날것 UTF-8이다.
- 모델의 한국어 능력 문제도 아니다 — 같은 모델·같은 시스템 프롬프트로 **tool 강제 없이
  평문**으로 시키면 오탈자 없이 깨끗하게 나온다.
- 즉 **강제 tool-call로 구조화 출력을 받는 경로 자체**에서만 생성 품질이 무너진다.

조건별 실측(깨진 문장 수 / 전체 문장 수):

| 출력 방식 | 모델 | 깨짐률 | `premises` |
| --- | --- | --- | --- |
| 강제 tool-call | sonnet-5 | 33/79 (41.8%) | 1~2개 (명세 2~4 미달) |
| 강제 tool-call | opus-5 | 11/190 (5.8%) | 4개 안정 |
| tool-call + `strict: true` | opus-5 | 8/39 (20.5%) | 0개로 붕괴 |
| 구조화 출력 | opus-5 | **0/83 (0%)** | 4개 안정 |
| 구조화 출력 | sonnet-5 | **0/61 (0%)** | 2개 안정 |

해결책이 아닌 것으로 확인된 것들:

- **`temperature` 하향** — Sonnet 5 / Opus 5에서 파라미터 자체가 제거되어 400을 반환한다.
- **`output_config.effort` 조정** — low/medium/high 간 깨짐률에 단조 관계가 없었고,
  출력 토큰도 안정적으로 줄지 않아 비용 손잡이로도 부적합했다.
- **`strict: true`** — 오히려 악화됐다. 출력에 `동`, `3d9종업계` 같은 문자열이 새어나오고
  구조 자체가 붕괴했다.
- **모델 상향(sonnet-5 → opus-5)** — 깨짐을 5.8%까지 줄이지만 0으로 만들지는 못한다.

## Decision

- `generateCritiqueAndPremises`는 **구조화 출력(`output_config.format` + `zodOutputFormat`)** 으로
  응답을 받는다. `tools` / `tool_choice`는 쓰지 않고, `src/lib/llm/tool.ts`는 삭제한다.
- **few-shot 예시는 유지한다.** 말투 통제(프롬프트 명세 원칙 1·5)를 담당하기 때문이다.
  다만 assistant 턴을 `tool_use` 블록이 아니라 **JSON 텍스트**로 되돌린다 — `tools`를
  선언하지 않은 요청에서는 `tool_use` 블록을 쓸 수 없다.
- **출력 형식 스키마에서는 모든 키를 필수로 두고, 값이 없을 수 있는 자리는 optional이 아니라
  nullable로 둔다.** 형식 스키마가 곧 모델에 대한 제약이므로 "키를 빼도 된다"는 여지를 주지 않는다.
  형식으로 표현할 수 없는 모순(예: `is_challengeable=true`인데 `counterpoints`가 빈 배열)은
  `findSemanticProblems`가 파싱 후에 따로 본다. 둘 다 "검증 실패 → 1회 재시도" 대상이다.
- `MAX_TOKENS`를 2048 → 8192로 올린다. 구조화 출력 실측 평균이 ~1,200 토큰이라 여유가 크고,
  `max_tokens`는 상한일 뿐이라 실제 사용량만 과금된다. 절삭은 두 번째 방어선으로
  `stop_reason === "max_tokens"`를 명시적으로 에러 처리한다.
- 클라이언트 타임아웃을 30초 → 60초로 올린다. 현행 모델은 thinking이 기본으로 켜져 있어
  30초를 넘기는 호출이 실측됐다.
- **모델은 `claude-sonnet-5`를 유지한다.** 구조화 출력 전환으로 sonnet-5의 깨짐도 0%가 되어
  모델을 올릴 이유가 사라졌고, opus-5 대비 콜당 비용이 약 1/3이다($0.016 vs $0.050).

## Consequences

- 사용자에게 노출되는 문구의 깨짐과 `premises` 누락이 함께 해소된다.
- sonnet-5는 6회 중 1회꼴로 `check_config` 누락(의미검증 실패)이 관측됐다. 기존 1회 재시도로
  잔존 확률은 ~3% 수준이지만, 재시도는 유상 호출이 한 번 더 나가는 것이므로 이 비율이 올라가면
  모델 상향(`client.ts`의 `CRITIQUE_MODEL` 한 줄)을 재검토한다. 세션당 호출 상한(20회)
  카운터는 재시도로 증가하지 않는다.
- opus-5는 전제를 4개, sonnet-5는 2개 내는 경향이 있다. 둘 다 명세 범위(2~4개) 안이지만
  결과 화면의 밀도가 달라지므로, 화면 품질을 올리고 싶을 때의 첫 번째 손잡이가 된다.
- **프롬프트 캐싱은 이번 스코프에서 도입하지 않는다.** 전환 전 구성에서는 입력 5,101토큰 중
  4,917토큰(96%)이 캐시 적중했지만, 구조화 출력으로 tool 정의가 빠지면서 입력 구성이 달라졌다
  (실측 3,853토큰). 캐싱은 별도로 측정해서 판단한다.
