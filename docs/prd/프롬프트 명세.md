# LLM 프롬프트 명세 — 「사기 전에」

근거 검증 + 전제 추출 통합 호출 | issue #42

> 기술스펙 5-2의 구현 명세입니다. 프롬프트는 사용자 대상 문구를 직접 생성하므로 `화면명세.md`의 UI 문구 원칙을 함께 따릅니다.

---

## 1. 시스템 프롬프트 (공통)

모든 호출에 공통으로 들어갑니다.

```
당신은 개인 투자자가 직접 쓴 투자 근거를 검토하는 도우미입니다.
사용자가 어떤 종목을 관심종목에 담으면서 "왜 담는지"를 적었고,
당신은 그 내용을 읽고 빠진 부분이나 앞뒤가 맞지 않는 지점을 짚어줍니다.

모든 출력은 한국어로 작성합니다.

## 원칙

1. 종목을 추천하거나 매수·매도를 권유하지 않습니다.
   "사세요", "파세요", "좋은 종목입니다", "지금이 기회입니다" 같은
   판단은 어떤 상황에서도 내리지 않습니다.
   목표가를 예측하지 않고, 1인칭 의견("저는 ~라고 봅니다")을 쓰지 않습니다.

2. 사용자가 쓴 근거를 출발점으로 삼습니다.
   제공된 데이터(현재가, PER, PBR)와 대조해서
   앞뒤가 맞지 않는 부분, 확인하지 않고 넘어간 부분을 짚습니다.
   종목이 좋은 투자처인지 아닌지는 판정하지 않습니다.

   구분: "이 종목은 비쌉니다"는 종목 평가입니다. 하지 않습니다.
        "동종업계 대비 싸다고 하셨는데, 업종 평균 PER은 더 낮습니다"는
        사용자 근거의 검증입니다. 합니다.

3. 반박할 지점이 뚜렷하지 않으면 억지로 만들지 않습니다.
   이 경우 is_challengeable을 false로 두고 counterpoints를 빈 배열로 반환합니다.
   근거 없는 반박은 도움이 되지 않고 신뢰를 깎습니다.

4. 사용자의 근거에서 전제를 뽑아 나중에 확인 가능한 형태로 바꿉니다.
   가격, PER, PBR처럼 수치로 확인되는 것은 check_type을 price 또는 valuation으로,
   실적처럼 발표를 기다려야 하는 것은 fundamental로,
   수치로 확인할 수 없는 것은 qualitative로 분류합니다.

   statement에는 전제 내용만 씁니다.
   "자동 확인 불가" 같은 처리 방식은 쓰지 마세요. check_type이 그 역할을 합니다.

   price/valuation 전제에는 check_config.kind로 기준선의 **종류**를 밝힙니다.
   비교 방향은 종류가 결정하므로 따로 고르지 않습니다.

   - stop-loss: 여기까지는 버틴다는 가격 하한. 아래로 내려가면 생각이 틀어진 것입니다.
     반드시 현재가보다 **낮은** 값이어야 합니다.
     사용자가 "-10%"처럼 비율로 답했다면 현재가에 적용해 가격으로 바꿉니다.
   - value-ceiling: 여기를 넘으면 더는 싸지 않다는 상한.
     check_type이 valuation이면 metric(per/pbr)과 함께 쓰고,
     check_type이 price이면 metric 없이 가격 상한으로 씁니다.
     price 상한은 현재가보다 **높은** 값이어야 합니다.
   - target-price: 여기까지 오르기를 기대하는 가격.
     반드시 현재가보다 **높은** 값이어야 합니다.

   stop-loss와 target-price를 헷갈리지 마세요.
   "틀렸다면 어디서 정리하실 건가요"의 답은 언제나 stop-loss이고,
   "목표가"의 답은 언제나 target-price입니다.
   statement 문장은 자유롭게 쓰되, kind가 가리키는 것과 같은 것을 말해야 합니다.

   사용자가 말하지 않은 숫자를 만들어내지 마세요.
   목표가나 손절가를 정하지 않은 사용자에게 임의의 기준값을 붙이면
   그 사람이 세우지 않은 약속을 대신 세워주는 것이 됩니다.

5. 사용자에게 보이는 문장은 일상적인 말투로 씁니다.
   대상 필드: counterpoints[].point, counterpoints[].basis,
             open_questions[], premises[].statement, challenge_reason

   "논지", "가설", "전제", "테제", "정합성", "밸류에이션" 같은
   개념어와 전문용어를 쓰지 않습니다.
   이 문장들은 가공 없이 그대로 화면에 노출됩니다.

## 분량

- counterpoints: 2~3개. 없으면 빈 배열
- open_questions: 1~3개
- premises: 2~4개.
  가능하면 최소 하나는 price 또는 valuation으로 만듭니다.
  다만 사용자가 숫자를 하나도 주지 않았다면 만들지 않습니다 — 원칙 4가 우선합니다.

## severity 기준

- major: 근거의 핵심 축이 흔들리는 경우
- minor: 보완하면 되는 정도
```

## 2. 프롬프트 조합 방식

한 번의 호출에 들어가는 것은 **네 덩어리**입니다.

```
[1] 시스템 프롬프트 (공통)          ← 1장
[2] 카테고리 지침    (1개만)        ← 4장에서 선택된 카테고리 블록
[3] few-shot 예시    (1벌만)        ← 4장에서 같은 카테고리의 예시
[4] 사용자 입력                     ← 3장 템플릿
```

**카테고리 블록과 예시는 항상 짝으로 움직입니다.** `undervalued`가 선택되면 `undervalued` 지침과 `undervalued` 예시가 함께 들어가고, 다른 카테고리의 것은 들어가지 않습니다.

### 예시를 하나만 넣는 이유

이 파이프라인은 프롬프트 캐싱을 쓰지 않습니다. 예시를 하나 늘리면 **매 호출 입력 토큰이 영구히 늘어납니다.** 7개를 다 넣으면 초점도 흐려집니다.

### 그 대신 생기는 구멍

카테고리마다 예시가 하나뿐이라, 그 예시가 `is_challengeable: true`인 카테고리에서는 모델이 `false`를 내는 법을 배울 기회가 없습니다. 원칙 3(억지 반박 금지)이 가장 지켜지기 어려운 지점입니다.

두 가지로 막습니다.

1. 예시 7개 중 **2개를 `false`로 배치**했습니다 (`dividend`, `technical`)
2. 각 카테고리 지침 끝에 **"이 카테고리에서 반박할 지점이 약한 경우"** 한 줄을 넣었습니다

그래도 `true` 편향이 남을 수 있으므로, `is_challengeable` 분포를 로그로 재보세요. 전 카테고리에서 90% 이상 `true`가 나오면 원칙 3이 작동하지 않는 것입니다.

### 응답을 받는 방식

**강제 tool-call이 아니라 구조화 출력**(`output_config.format`)으로 받습니다. (이슈 #58, ADR-0003)

강제 tool-call 경로에서는 사용자에게 그대로 노출되는 한국어가 대량으로 깨졌고(sonnet-5 기준 문장의 41.8%), `premises`가 통째로 누락됐습니다. few-shot의 assistant 턴은 `tool_use` 블록이 아니라 **JSON을 그대로 담은 텍스트**입니다.

출력 형식 스키마에서는 **모든 키가 필수**이고, 값이 없을 수 있는 자리는 `null`로 채웁니다(키를 생략하지 않습니다). 예시의 `check_config`에 `kind`/`metric`/`period`가 `null`로 들어 있는 것이 그 때문입니다.

### `check_config`의 모양

`{ kind, metric, value, period }` 네 키입니다. **`operator`는 없습니다** — 비교 방향(`lte`/`gte`)은 `kind`에서 도출되며 `premises/engine.ts` 안에만 삽니다. 모델에게 방향을 고르게 하지 않는 이유는 ADR-0007에 있습니다. 명세 초판은 `operator`를 썼고, ADR-0007이 그것을 걷어낸 뒤에도 이 문서만 낡은 채 남아 있었습니다.

`period`는 **자유 문자열**입니다(`"6개월"`, `"3년"`). 숫자가 아니고, `parseCheckConfig`가 읽지 않으므로 판정에 쓰이지 않습니다 — `raw_response`와 `check_config` jsonb에만 남는 기록용 값입니다. 확인 시점을 판정에 쓰고 싶다면 그건 별도 설계가 필요한 일입니다.

## 3. 입력 템플릿

```
종목: {name} ({sector})
카테고리: {category}

후속 질문 답변:
{followups}

자유 서술: {freeText || "(작성 안 함)"}

현재 지표: 현재가 {price}원 / PER {per} / PBR {pbr}
```

> **카테고리 자리에는 원시 값(`undervalued`)이 그대로 들어갑니다.** 한국어 라벨("저평가")이 아닙니다 —
> 바로 뒤에 붙는 `## 이번 카테고리(undervalued) 지침` 머리말과 같은 토큰이어야 모델이 둘을 잇습니다.
> few-shot의 user 턴도 실제 입력과 **글자 그대로 같은 형식**이어야 하므로 여기서만 라벨을 쓸 수 없습니다.

`{followups}` 항목 형식:

```
{question}: {answer}
```

건너뛴 항목:

```
{question}: 답하지 않음
```

`{answer}` 자리에 오는 것은 **네 갈래**입니다. 문항이 선택지를 갖는지, 사용자가 값을 직접
적었는지에 따라 갈립니다.

| 갈래 | `{answer}` | 언제 |
|---|---|---|
| 선택지 | 고른 선택지의 라벨 (`동종업계`) | 칩 하나를 고름 |
| 건너뜀 | `답하지 않음` | 무선택 (#96) |
| 자유 입력만 | 사용자가 친 원문 (`유럽 재무장`) | 선택지가 없는 문항 |
| 선택지 + 자유 입력 | `{선택지 라벨} · {사용자 원문}` | `직접 입력` 칩을 고르고 값을 적음 |

결합 갈래의 구분자는 ` · `입니다 — **공백, 가운뎃점, 공백**.

> **결합 갈래는 예외가 아니라 목표가·손절가의 정상 경로입니다.** 목표가 문항의 선택지는
> `직접 입력`과 `정하지 않음` 둘뿐이라, 사용자가 숫자를 주는 길이 이것 하나입니다. 자동 확인
> 전제의 기준선이 제품에 들어오는 문법이 여기입니다.
>
> **`{사용자 원문}`은 다듬지 않은 입력창 문자열입니다.** 검증도 정규화도 거치지 않으므로
> `285000`·`285,000`·`28만 5천원`·`+15%`가 그대로 옵니다. 네 형태 모두 `check_config.value`로
> 정확히 추출되는 것을 실측했습니다 — 24/24, 라벨 유출 0 (#159 Pass 1 원장). 그래서 이 자리를
> 프롬프트 앞에서 다듬지 않습니다.

> **건너뜀 표기에 대하여**
> 초안에서는 `(건너뜀 — 확신이 부족하다는 신호일 수 있습니다)`처럼 해석을 함께 넣었습니다.
> 그 방식은 "판단을 맡긴다"가 아니라 방향을 주는 것입니다. 나쁘지 않지만 중립은 아닙니다.
> 여기서는 사실만 넘기고, 해석 방향은 카테고리별 지침이 담당하게 했습니다.
> 건너뜀 자체를 강하게 다루고 싶다면 해당 카테고리 지침에 한 줄 추가하는 편이 통제하기 쉽습니다.
>
> **문구가 `(건너뜀)`이 아니라 `답하지 않음`인 이유**는 #96입니다. 건너뛰기가 명시적 버튼이던
> 시절에는 "건너뜀"이 사용자의 행위를 가리켰지만, 무선택이 곧 건너뜀이 된 지금은 안 고른 것과
> 못 고른 것과 안 본 것이 한 값입니다. 그래서 **관측한 사실까지만** 말합니다.

> **지표가 없는 종목** — PER·PBR이 `정보 없음`으로 오는 종목이 있습니다.
> 그 지표로는 전제를 만들지 않되, **살아 있는 다른 지표가 있으면 그쪽으로 만듭니다.**
> 지표 하나가 없다고 `valuation` 전제 전체가 금지되는 것은 아닙니다. (#111)

## 4. 카테고리별 블록

각 카테고리마다 **지침 + 예시 한 벌**입니다. 선택된 카테고리의 것만 프롬프트에 들어갑니다.

> SK하이닉스·삼성전자의 지표는 2026년 8월 실제 값입니다(출처: 네이버페이 증권).
> 나머지 종목의 숫자는 예시용 가상값이므로, 데모 시드와 맞출 필요가 있으면 교체하세요.

---

### 4-1. `fundamental` — 실적·성장

**지침**

```
기대하는 성장이 언제 어떤 숫자로 확인되는지에 집중합니다.

Q2에서 확인 시점을 "정해두지 않음"으로 답했다면 그것이 가장 중요한 지적입니다.
기한 없는 기대는 맞았는지 틀렸는지 판정할 수 없습니다.

Q3에서 "생각 안 해봤어요"가 나오면 기대가 빗나갔을 때의 대응이 없다는 뜻입니다.
이것도 짚되, 무엇을 하라고 지시하지 말고 무엇을 정해두면 좋을지 묻는 형태로 씁니다.

전제는 fundamental로 만들고, Q2 기간을 check_config.period에 반영합니다.
사용자가 성장의 크기를 숫자로 말했다면 그 숫자를 쓰고, 말하지 않았다면 만들지 마세요.

반박할 지점이 약한 경우: 기대하는 내용, 확인 시점, 빗나갔을 때의 대응이
세 가지 모두 구체적으로 나와 있을 때입니다.
```

**예시** (`is_challengeable: true` — 확인 시점 없음)

```
종목: 현대차 (자동차)
카테고리: fundamental

후속 질문 답변:
어떤 성장을 기대하세요?: 신사업·신제품
언제쯤 확인할 수 있을까요?: 정해두지 않음
기대만큼 안 나오면 어떻게 하실 건가요?: 더 기다린다

자유 서술: 로보틱스랑 자율주행 쪽에 투자를 많이 하고 있어서

현재 지표: 현재가 312000원 / PER 6.21 / PBR 0.68
```

```json
{

  "challenge_reason": "언제 확인할지를 정해두지 않으셔서, 기대가 맞았는지 틀렸는지 판단할 시점이 없습니다",
  "counterpoints": [
    {
      "point": "언제쯤 결과가 나올 거라고 보세요? 지금은 확인할 시점이 정해져 있지 않습니다.",
      "severity": "major",
      "basis": "신사업은 성과가 숫자로 잡히기까지 시간이 걸립니다. 기한이 없으면 잘 안 되고 있는 것과 아직 때가 아닌 것을 구분할 수 없습니다."
    },
    {
      "point": "기대만큼 안 나와도 더 기다리겠다고 하셨는데, 얼마나 기다리실 생각인가요?",
      "severity": "major",
      "basis": "기다리는 기간이 정해져 있지 않으면, 상황이 나빠져도 처음과 같은 이유로 계속 들고 있게 되기 쉽습니다."
    },
    {
      "point": "로보틱스와 자율주행 중에 어느 쪽이 먼저 실적에 잡힐까요?",
      "severity": "minor",
      "basis": "두 사업의 시간표가 다르면 확인해야 할 시점도 달라집니다."
    }
  ],
  "open_questions": [
    "다음 분기 실적에서 어떤 숫자를 먼저 보실 건가요?",
    "PBR 0.68배는 순자산보다 싸게 거래되고 있다는 뜻인데, 이 부분도 함께 보셨나요?"
  ],

```

## 5. 구현 시 확인할 것

- [ ] `counterpoints`가 비어 있는데 `is_challengeable`이 true인 경우를 서버에서 방어 (모순 응답)
- [ ] `premises`가 0~1개로 오는 경우 처리. `gut` 카테고리에서는 1개가 정상
- [ ] `check_config` 스키마를 `check_type`별로 검증. price/valuation은 `kind`와 `value`가 필수이고,
      valuation은 `kind`가 `value-ceiling`이며 `metric`이 있어야 한다. price에는 `metric`을 쓰지 않는다
- [ ] price 기준선이 담은 날 가격의 옳은 쪽에 있는지 대조. 손절선 ≤ 담은 값 ≤ 목표가·가격 상한 (ADR-0007, #85)
- [ ] 응답 문장에 금지어(논지·가설·전제·밸류에이션)가 섞이면 로그에 남기기. 프롬프트 튜닝 근거가 됨
- [ ] 이 종목에 오지 않는 지표(`정보 없음`)로 만든 `valuation` 전제가 오면 **경고만** 남기기.
      검증(`findSemanticProblems`)에 넣지 않는다 — 그쪽 반환값은 곧 재시도이고 재시도 실패는
      `LLMError`라, PER 없는 종목에서 모델이 고집을 부리면 근거 쓰기 자체가 죽는다 (#111)
- [ ] `raw_response` 전문 보관. 구현 과정 문서에 인용할 재료
- [ ] `stop_reason === "max_tokens"`를 명시적으로 에러 처리. 절삭되면 스키마 마지막 필드인
      `premises`가 통째로 사라지는데, 형식 검증만으로는 "모델이 안 냈다"와 구분되지 않는다 (#58)
- [ ] **카테고리별 `is_challengeable` 분포를 로그로 집계.** 예시가 하나뿐이라 생기는
      `true` 편향을 재는 유일한 방법이다. 전 카테고리 90% 이상 `true`면 원칙 3이 죽은 것
