## 0. 용어 규칙

세 층위로 나눠 씁니다. 하나의 단어로 전부 덮으려 하지 않습니다.

| 층위 | 사용 어휘 | 예시 |
|---|---|---|
| 코드 · DB | 영어 식별자 | `thesis`, `premise`, `critique` |

## 1. 확정된 결정사항

| 항목 | 결정 | 근거 |
|---|---|---|
| 인증 | 없음. 익명 세션(httpOnly 쿠키) | 심사자 진입 마찰 0. 세션별 데이터 격리 |
| 폼팩터 | 모바일 뷰포트 고정 (**402×874**), 데스크톱에서는 중앙 정렬 + 여백 | 입력 설계의 전제가 모바일. MTS 맥락 유지 |
| 구현 범위 | ①②③④ 실동작, ⑤는 자동 판정 가능한 전제만 | 4일 제약. 한계를 제품 안에 드러냄 |
| 시간 시연 | 데모 시나리오 모드 ("3개월 후로 이동") | 붕괴 감지를 동작으로 증명 |
| 증권사 API | 한국투자증권. **조회는 실전 도메인, 거래는 모의투자** | 재무비율이 모의 도메인에서 제공되지 않음. 5-1 참조 |
| LLM | Anthropic API (Claude) | 기존 작업 환경. structured output 사용 |
| 종목 범위 | 국내주식, 데모용 20~30종목 화이트리스트 | 재무 데이터 사전 캐싱으로 응답 속도 확보 |
| 알림 | 인앱 배지·목록만. 푸시·이메일 없음 | 4일 범위 밖 |
| DB | Neon (Postgres) + Drizzle ORM | 아래 참조 |

> **DB 선택 경위** — 처음에는 Supabase를 상정했으나 무료 티어 프로젝트 한도(2개)가 이미 차 있었습니다. 기존 프로젝트를 일시정지하면 포트폴리오에 링크한 데모 두 곳이 죽기 때문에 새 제공자를 쓰기로 했습니다.
> Render 무료 Postgres는 생성 후 30일에 만료되고 14일 유예 후 데이터까지 삭제되므로, 채용 절차가 몇 주 이어질 것을 감안해 만료가 없는 Neon을 택했습니다.
> 이 프로젝트는 Auth·Realtime·Storage를 쓰지 않아 사실상 호스팅 Postgres만 필요하므로 교체 비용은 없습니다.

## 2. 기술 스택

```
Frontend    Next.js (App Router) + TypeScript + Tailwind + shadcn/ui
Backend     Next.js Route Handlers / Server Actions
DB          Neon (Postgres) + Drizzle ORM
외부연동     한국투자증권 REST API (실전 조회 / 모의 거래)
```

DB는 호스팅 Postgres면 무엇이든 대체 가능합니다. 스키마와 쿼리는 표준 Postgres라 제공자를 바꿔도 코드가 그대로입니다. 

Invest Diary 프로젝트 에서 검증한 **한투 API 어댑터 계층만 이식**합니다. 나머지는 새 저장소에서 새로 작성합니다.

## 3. 데이터 모델

```sql
-- 익명 세션
sessions (
  id              uuid PK,
  created_at      timestamptz,
)
-- 데모 시점(7장)은 세션 컬럼이 아니라 클라이언트 값입니다. 서버는 조회 시
-- 인자로 받을 뿐 어느 시점을 보고 있는지 기억하지 않습니다.

-- 관심종목 / 보유종목
watchlist_items (
  id              uuid PK,
  session_id      uuid FK,
  ticker          text,            -- 종목코드 6자리
  name            text,
  status          text,            -- watching | bought | removed
  added_price     numeric,         -- 담은 시점 가격 (근거 유효성 기준)
  added_at        timestamptz,
  avg_buy_price   numeric,         -- 매수 단가 (손익 기준). status=bought일 때만
  bought_at       timestamptz,
  is_seed         boolean default false,
  created_at      timestamptz
)

-- 투자 근거 (버전 관리)
theses (
  id              uuid PK,
  watchlist_item_id uuid FK,
  version         int default 1,
  category        text,            -- fundamental|undervalued|theme|dividend|technical|recommended|gut
  followup        jsonb,           -- 후속질문 답변. 건너뛴 질문도 skipped로 기록
  free_text       text,            -- 선택 입력
  created_at      timestamptz
)

-- AI 검증 결과
critiques (
  id              uuid PK,
  thesis_id       uuid FK,
  is_challengeable boolean,        -- 반박할 만한지 판정
  counterpoints   jsonb,           -- [{point, severity, basis}]
  open_questions  jsonb,
  raw_response    jsonb,           -- 원본 보관 (디버깅·문서화용)
  created_at      timestamptz
)

-- 확인 가능한 전제
premises (
  id              uuid PK,
  thesis_id       uuid FK,
  statement       text,            -- "PER 15배 이하 유지"
  check_type      text,            -- price | valuation | fundamental | qualitative
  check_config    jsonb,           -- {metric, operator, value, period}
  status          text,            -- intact | broken | pending | manual
                                   -- fundamental/qualitative 전제에만 의미가 있습니다.
                                   -- price/valuation 전제의 status는 저장하지 않고
                                   -- 조회 시 계산합니다 (6장).
  observed_value  text             -- 위와 동일. 자동 전제는 계산값입니다.
)

-- 주문 시점 행동 기록 (핵심 지표 수집)
order_events (
  id              uuid PK,
  session_id      uuid FK,
  watchlist_item_id uuid FK,
  thesis_shown    boolean,
  initial_qty     int,             -- S4에서 수량 입력을 걷어낸 뒤로는 늘 1입니다 (#143).
  final_qty       int,             -- 컬럼을 떨어뜨리지 않는 이유는 화면명세 S4에 있습니다.
  action          text,            -- proceed | cancel | update_thesis
                                   -- adjust는 수량 입력과 함께 발생하지 않게 됐습니다 (#143).
  created_at      timestamptz
)
```

> **가격 필드가 둘인 이유** — 근거가 아직 유효한지는 `added_price` 기준으로 판정하고, 실제 손익은 `avg_buy_price` 기준으로 표시합니다. 담은 시점과 산 시점이 다를 수 있어 하나로는 둘 다 표현할 수 없습니다. (화면명세 S5 참조)

**세션 격리 원칙** — 모든 조회 쿼리는 `session_id` 필터를 반드시 거칩니다.

익명 쿠키 세션을 쓰므로 DB의 RLS는 적용하지 않습니다. RLS는 인증 토큰과 물려 동작하는 구조라 이 인증 모델에는 맞지 않습니다. 대신 **서버 레이어에서 단일 진입점으로 강제**합니다.

- 세션 ID는 서버에서만 읽습니다 (httpOnly 쿠키). 클라이언트가 임의로 지정할 수 없습니다
- 모든 DB 접근은 `session_id`를 인자로 받는 헬퍼를 거칩니다. 쿼리를 직접 작성하지 않습니다
- 리소스 ID로 조회할 때도 소유 세션을 함께 검증합니다 (다른 세션의 UUID를 알아내도 조회 불가)

## 5. 외부 연동

### 5-1. 한국투자증권 API — 도메인 분리

**모의투자 도메인에서는 재무비율을 제공하지 않습니다.** 밸류에이션 전제(PER/PBR)를 쓰려면 조회를 실전 도메인으로 보내야 합니다.

그래서 클라이언트를 둘로 나눕니다. 같은 클래스에 플래그로 분기하지 말고 **파일부터 분리해서, 거래 코드 경로가 실전 자격증명을 참조할 방법이 아예 없게** 만듭니다. 실수로 실계좌에 주문이 나가는 사고를 구조적으로 차단하기 위해서입니다.

```
lib/kis/quote-client.ts   실전 도메인 · 조회 전용 · 읽기만
lib/kis/trade-client.ts   모의 도메인 · 주문/잔고 · 쓰기
```

| 용도 | 엔드포인트 | 클라이언트 |
|---|---|---|
| 접근토큰 발급 | `/oauth2/tokenP` | 양쪽 각각. 유효기간 24h, **반드시 캐싱** |
| 현재가 시세 (PER/PBR 포함) | `/uapi/domestic-stock/v1/quotations/inquire-price` | quote |
| 재무비율(eps/bps/roe 등) | `/uapi/domestic-stock/v1/finance/financial-ratio` | quote (실전 전용) |
| 잔고 조회 | `/uapi/domestic-stock/v1/trading/inquire-balance` | trade |
| 현금 주문 | `/uapi/domestic-stock/v1/trading/order-cash` | trade |

> **TR_ID는 실전과 모의가 다릅니다.** 각 클라이언트 파일 안에 상수로 두고 섞이지 않게 하세요.
> Rate limit이 있으므로 목록 화면에서 종목별 개별 호출 대신 배치 + 캐싱(30~60초)으로 처리합니다.
> **PER/PBR은 재무비율 API가 아니라 현재가(`inquire-price`) 응답에 실려 옵니다** — 실 API 검증 결과(issue #13, `docs/research/kis-financial-ratio.md`). 밸류에이션 전제 판정에는 현재가 호출 한 번이면 충분하며, 재무비율 API는 `eps`/`bps`/`roe_val` 등 현재가에 없는 필드가 필요할 때만 별도 호출합니다.

**환경변수 명명** — 용도가 이름에서 드러나게 합니다.

```
KIS_REAL_APPKEY_READONLY / KIS_REAL_APPSECRET_READONLY
KIS_MOCK_APPKEY / KIS_MOCK_APPSECRET / KIS_MOCK_ACCOUNT
```



### 5-2. Anthropic API

**호출은 서버에서만.** 클라이언트 번들에 키가 들어가면 안 됩니다.

**호출 1회로 통합** — 검증과 전제 추출을 한 번에 받습니다. 라운드트립을 줄여 체감 속도를 확보합니다.

입력: 종목명·업종, 카테고리, 후속질문 답변(건너뛴 항목 포함), 자유 서술, 종목 기본 지표(현재가·PER·PBR)

출력 스키마:

```json
{
  "is_challengeable": true,
  "challenge_reason": "'실적이 좋다'에 머물러 있고 밸류에이션 판단이 없음",
  "counterpoints": [
    { "point": "...", "severity": "major|minor", "basis": "..." }
  ],
  "open_questions": ["..."],
  "premises": [
    {
      "statement": "PER 15배 이하 유지",
      "check_type": "valuation",
      "check_config": { "metric": "per", "operator": "lte", "value": 15 }
    },
    {
      "statement": "경쟁사가 이 시장에 진입하지 않는다",
      "check_type": "qualitative",
      "check_config": { "remind_after_days": 90 }
    }
  ]
}
```

**프롬프트 원칙 (시스템 프롬프트에 명시)**

1. 종목을 추천하거나 매수·매도를 권유하지 않는다
2. 사용자가 쓴 근거의 내부 정합성만 다룬다
3. 반박할 지점이 약하면 억지로 반박하지 않고 `is_challengeable: false`를 반환한다
4. 전제는 반드시 관측 가능한 형태로 변환한다. 불가능하면 `qualitative`로 분류한다
5. 출력 문장은 "논지", "가설" 같은 개념어 대신 일상어를 쓴다

**안전장치** — 세션당 LLM 호출 상한(예: 20회), 요청 타임아웃, 실패 시 재시도 1회.

## 6. 전제 판정 엔진

`check_type`에 따라 판정기를 분기합니다.

| check_type | 판정 방법 | 4일 내 구현 |
|---|---|---|
| `price` | 현재가 vs 기준값 비교 | ✅ |
| `valuation` | 현재가(`inquire-price`) 응답의 PER/PBR vs 기준값 | ✅ |
| `fundamental` | 분기 실적 조회 후 비교 | △ 데모 시나리오로 대체 |
| `qualitative` | 자동 판정 불가. `manual` 상태로 리마인드만 | ✅ (판정 안 함) |

**자동 전제는 저장하지 않습니다** — `price`/`valuation` 판정은 시세와 기준값만 있으면 결정되는 순수 계산입니다. 결과를 DB에 쓰지 않고 조회할 때마다 계산합니다. S5의 "기준 PER 15배 → 현재 21.3배"도 저장된 값이 아니라 그 자리에서 나오는 계산값입니다.

따라서 **실행 주기라는 개념이 없습니다.** 배치도 Cron도 "판정 트리거"도 두지 않습니다 — 아무도 판정을 돌리지 않고, 목록·상세·주문 시트 어디서 조회하든 그 시점의 시세로 상태가 나옵니다.

`fundamental`/`qualitative` 전제는 반대입니다. 자동 판정 대상이 아니므로 `premises.status`에 저장된 값(시드 프로비저닝 또는 사용자의 직접 확인으로 정해진 값)을 그대로 읽습니다. 같은 `Premise` 안에서 status의 출처가 둘로 갈리며, 이 구분은 조회 계층 안에 갇힙니다 — 배지를 그리는 쪽은 합쳐진 결과만 봅니다.

> **왜 저장하지 않는가** — 데모 시점(7장)이 판정의 입력이기 때문입니다. 저장하면 `현재` 판정과 `3개월 후` 판정이 같은 행을 서로 덮어써서, 마지막으로 조회한 시점이 무엇이었냐에 따라 화면이 달라집니다. (ADR-0004)

## 7. 데모 시나리오 모드

붕괴 감지는 원래 수 주~수 개월이 걸립니다. 사용자가 30초 안에 코어 가치를 체험하도록 시간 이동을 제공합니다.

**동작**

- 상단 토글: `현재` ↔ `3개월 후`
- **데모 시점은 화면 표시 옵션이 아니라 전제 판정의 입력입니다.** 시점이 바뀌면 가격만이 아니라 배지 상태와 변동 배너도 함께 바뀝니다. 시점을 받는 모든 조회(목록·상세·주문 시트)가 같은 값을 써야 하며, 어느 하나가 다른 시점의 결과를 들고 있으면 안 됩니다.
- 토글 값은 클라이언트에 두고 조회 인자로 넘깁니다(`sessions`에 저장하지 않음)
- 시드 종목에 한해 미리 준비한 시나리오 데이터(가격·PER 변화)를 사용
- 사용자가 직접 추가한 종목은 실제 데이터를 그대로 사용



**정직성 확보** — 화면 상단에 배너를 고정합니다.

> "데모 모드입니다. 시드 종목의 3개월 후 데이터는 시연을 위해 준비한 가상 값입니다."



**시드 종목 구성 (3종목)**

한 종목에 전제를 2~3개 두고, 그중 일부만 깨지게 합니다. 전부 깨지는 것보다 현실적이고 화면도 풍부해집니다.

| 시드 | 상태 | 구성 |
|---|---|---|
| 종목 A | 근거 작성됨 | **가격 상승으로 전제 붕괴.** "3만원 아래면 싸다" → 4만 2천원 |
| 종목 B | 근거 작성됨 | **밸류에이션 붕괴 + 일부 유지.** "PER 15배 이하" → 21배 (깨짐) / "배당 유지" → 유지 / `qualitative` 전제 1개 |
| 종목 C | **비어 있음** | 심사자가 직접 담아보고 입력해볼 대상 |



종목 A가 가장 인상적인 케이스입니다. **가격이 올랐는데 전제가 깨진** 상황이라, 좋은 소식인데 내 근거는 무효가 된 미묘한 지점을 보여줍니다. 단순한 손실 경고보다 제품의 성격을 잘 드러냅니다.

종목 B에 `qualitative` 전제를 섞는 이유는 `직접 확인 필요` 배지를 화면에 노출시키기 위해서입니다. 자동 판정의 한계를 감추지 않고 제품 안에 드러냅니다.

종목 C를 비워두는 이유는, 시드가 전부 채워져 있으면 심사자가 직접 입력해볼 유인이 사라지기 때문입니다. 코어 루프를 직접 통과해봐야 제품이 이해됩니다.
